# ALLIN — инструкции проекта

This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, accessibility, and cross-platform compatibility.

## Архитектура

- При изменении границ модулей, навигации, состояния или доступа к данным используй [docs/architecture.md](docs/architecture.md) как источник истины.
- `app/` содержит только маршруты и навигаторы. Экраны и бизнес-логика находятся в `features/`.
- API предметной области размещай в `features/<domain>/api/`; общий HTTP-клиент находится в `shared/api/`, Supabase-клиент — в `shared/api/supabase/`. Не создавай технические каталоги `services` и общие файлы запросов нескольких фич. `features/services/` — предметная область услуг.
- Весь общий код находится в `shared/`: UI — в `shared/components/`, тема — в `shared/theme/`, инфраструктура — в `shared/lib/`, общее состояние — в `shared/store/`. Состояние фичи находится в `features/<domain>/store/`. Не возвращай корневые `components`, `core`, `contexts`, `hooks`, `lib`, `constants` или совместимые пути-переэкспорты.
- Имена каталогов и файлов — `kebab-case`; имена компонентов и типов — `PascalCase`. Исключения: специальные файлы Expo Router (`_layout.tsx`, группы маршрутов), стандартные `README.md`/`AGENTS.md`, сторонние навыки и ресурсы. Общий компонент размещай в `shared/components/<component-name>/index.tsx`; платформенные реализации — в той же папке (`index.ios.tsx`).
- Во всех фичах используй одинаковые разделы: `api`, `components`, `hooks`, `screens`, `store`, `types`, `utils`. Не смешивай `store/stores`, `helpers/utils`, `services/api`. Пустая папка с `.gitkeep` обозначает место для реализации, а не готовую функцию.
- Импортируй компонент из его собственной папки. В `shared/components` нет общего barrel-файла, который загружает все компоненты. Между модулями предпочитай alias `@/`.
- При изменении реализованной архитектуры обновляй `docs/architecture.md`. Не описывай планы как готовую функциональность.
- При изменении состояния, запросов и границ функций применяй проектный [feature-boundaries](.agents/skills/feature-boundaries/SKILL.md). Каждое состояние имеет одного владельца; взаимодействие областей использует явные параметры и доменные API, без объединения чужих stores в универсальную сессию.

## Скиллы

- Каталог перенесённых навыков: [docs/skills.md](docs/skills.md). `expo-project-structure` применяется только к новым проектам; в этом репозитории соблюдай существующую структуру без обязательного переноса в `src/`.

- Выбирай минимальный набор скиллов по задаче и перед применением полностью читай соответствующий `SKILL.md`. Инструкции пользователя имеют приоритет над рекомендациями скилла.
- Новый или существенно изменяемый экран: `expo-native-ui` + `expo-design-system`; для финальной UI-проверки — `emil-design-eng` с применением только React Native-совместимых рекомендаций.
- Нативные контролы `@expo/ui`: `expo-ui`. Навигация и маршруты: `expo-router`. Запросы и серверные состояния: `expo-data-fetching`.
- Анимации, жесты, переходы и haptics: проектный `expo-animation`. Не подключай одновременно дублирующий `animate-expo`.
- `break-ui` применяй по запросу на стресс-тест. `find-animation-opportunities` и `improve-animations` — только для read-only аудита. `review-animations` и `prototype` — только по явному запросу.
- Не применяй web-only скиллы к нативным экранам: `design-taste-frontend`, `animate`, `animation-performance`, `mobile-native`, `ask-sonner`, `pick-ui-library`.
- Для вопросов о Codex, скиллах и продуктах OpenAI используй `openai-docs`.
- Проектные скиллы размещай в `.agents/skills/<имя>/SKILL.md`. Если упомянутый скилл недоступен, сообщи об этом и используй лучший доступный подход.

## UI/UX экранов

Перед реализацией определи задачу пользователя, главное действие, порядок блоков и необходимые loading, empty, error, disabled и success-состояния. Проверь соседние экраны, `shared/components/` и `shared/theme/`.

- Не располагай элементы произвольно: структура должна следовать пользовательской задаче и ясной визуальной иерархии.
- Используй токены темы и 4-point сетку. Не дублируй палитру, типографику и стили общих компонентов внутри экранов.
- В текстовых подписях вместо набранного ALLIN используй `AllinText` из `shared/components/allin-text`: знак подстраивается под `fontSize` подписи и системный масштаб. Отдельные логотипы (splash, вход, блок бренда) используют `AllinLogo` в своём размере. Не заменяй текст в данных, поиске, email, идентификаторах и доступных названиях.
- Выравнивай контент по общим направляющим; связанные элементы группируй, смысловые группы разделяй увеличенным интервалом.
- На экране должно быть одно очевидное primary-действие, если сценарий не требует иного.
- Не превращай каждый блок в карточку и не добавляй декоративные эффекты или анимацию без функциональной причины.
- Не дублируй заголовок маршрута внутри контента, если его уже показывает navigation header.
- Сначала переиспользуй `shared/components/`. Применяй `@expo/ui`, только когда он установлен и подходит задаче. Новую UI-зависимость добавляй только при отсутствии подходящего существующего решения.
- Выноси общий компонент, когда он используется минимум на двух экранах, имеет понятную роль и API проще его реализации.
- Учитывай safe area, клавиатуру, прокрутку, маленькие экраны, длинный текст и Dynamic Type.
- Всегда предотвращай непреднамеренные сдвиги разметки при смене состояний: появлении иконок, отметок, индикаторов загрузки и изменении счётчиков. Заранее резервируй место под условные элементы; для рамок сохраняй постоянную толщину и меняй только цвет. Соседний контент и кнопки не должны смещаться. Не добивайся стабильности отключением Dynamic Type или обрезанием важного текста.
- В JSX-разметке экранов и компонентов добавляй короткие комментарии на русском перед смысловыми UI-блоками: что блок показывает и при каком условии появляется. Поясняй также решения, предотвращающие сдвиги разметки. Комментируй назначение блока, а не каждый тег; обновляй комментарии вместе с кодом.
- Минимальная интерактивная область — 44×44 pt. Добавляй pressed/disabled/loading/selected состояния и корректные accessibility props.
- Для длинных коллекций используй виртуализированный список; не вкладывай большой `FlatList` в вертикальный `ScrollView`.
- Skeleton показывай на месте будущего контента; не создавай отдельный loading-route и не показывай empty-state до завершения первой загрузки.
- Если доступен визуальный запуск, проверь экран в светлой и тёмной теме и выполни цикл screenshot → исправление → повторная проверка.

## Навигация

- Каждая самостоятельная бизнес-задача или действие получает отдельный экран и Expo Router route. Не переключай бизнес-содержание универсального экрана параметрами `section`, `action` или `mode`, если пользователь явно не запросил такой сценарий.
- Общие loading, error, empty, success и access-состояния могут использовать переиспользуемый компонент или общий status screen; отдельный маршрут на каждое состояние не нужен.
- Файлы маршрутов и `_layout.tsx` находятся в `app/`; компоненты, hooks и бизнес-логика — вне `app/`.
- Импортируй навигационные API из `expo-router`.

## Expo и зависимости

- Перед использованием Expo, EAS или React Native API прочитай версию `expo` в `package.json`, затем открой документацию для этой версии. Используй [Expo llms.txt](https://docs.expo.dev/llms.txt) как индекс к актуальной странице; не полагайся на память об API.
- Устанавливай пакеты через `npx expo install <package>`, чтобы получить совместимую с текущим SDK версию. В этом проекте используется npm (`package-lock.json`, без `bun.lock`).
- Предпочитай поддерживаемые Expo-модули сторонним библиотекам.
- Проект использует Continuous Native Generation: пока `ios/` и `android/` отсутствуют, не создавай и не редактируй их вручную; нативную конфигурацию задавай через app config и config plugins.
- После добавления native dependency проверь по документации, требуется ли development build; не предполагай совместимость с Expo Go.

## Форматирование кода

- Перед объявлениями функций, hooks и компонентов добавляй краткий комментарий на русском, предпочтительно JSDoc (`/** ... */`). Для функции поясняй решаемую задачу, смысл входных данных и результата; для hook — какие данные или состояние он предоставляет и как используется; для компонента — что он отображает, в каком сценарии нужен и как ключевые props влияют на поведение. Указывай существенные побочные эффекты и ограничения, если они есть. Соразмеряй подробность сложности кода, не пересказывай имя или типы и не добавляй шаблонные пояснения к очевидным inline-callback. Обновляй комментарии вместе с реализацией.
- Пиши код в читаемом формате, как после Prettier: используй корректные отступы, переносы строк и пустые строки между смысловыми блоками.
- Не сжимай несколько инструкций, условия, обработчики и JSX-разметку в одну строку. Длинные списки props, аргументов и свойств объектов переноси на отдельные строки; короткие простые выражения могут оставаться однострочными.
- Разделяй пустыми строками подготовку данных, обработчики, вычисления и возвращаемую разметку, а внутри JSX — самостоятельные смысловые блоки. Не добавляй пустую строку после каждой строки кода.
- Соблюдай существующую конфигурацию форматирования проекта. Если форматтер настроен, применяй его к изменённым файлам; не переформатируй несвязанные файлы.

## Проверка

- После изменения кода запускай `npm run lint` и `npm run typecheck`. Дополнительно запускай относящиеся к изменению тесты.
- Исправляй только ошибки, вызванные запрошенным изменением; существующие несвязанные проблемы явно указывай в результате.
- Не объявляй UI готовым только по статическим проверкам, если доступна проверка на целевом устройстве или симуляторе.
- При UI-проверке переключай loading, disabled, selected и success-состояния, изменяй счётчики и проверяй появление/исчезновение условных элементов: размеры блоков и положение соседних элементов должны оставаться стабильными, если сценарий не предполагает изменения структуры.
